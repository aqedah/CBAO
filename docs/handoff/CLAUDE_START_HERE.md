# Claude 개발 지시서 — AI Office 픽셀 사무실

## 수행할 일

기존 AI Office에 **따뜻한 2.5D 등각투영 픽셀 사무실 보기**를 실제로 구현하라. 메인 대시보드는 유지한다. GPT, Claude, Gemini, NotebookLM, Codex에게 고정된 작업석과 독립 캐릭터를 두고, 실제 업무 상태를 같은 데이터 저장소에서 받아 표시하라.

단순 이미지를 배경으로 깔고 버튼 몇 개를 얹는 것을 최종 구현으로 제출하지 마라. 바닥·가구·캐릭터·상태 UI를 분리하고, 위치·상태·선택이 독립적으로 바뀌게 하라. 생성 이미지는 분위기 참고일 뿐이다.

## 먼저 읽을 파일

1. `SPEC_DELTA.md`: 기존 명세에서 변경되는 부분.
2. `PIXEL_OFFICE_SPEC.md`: 제품과 화면 기준.
3. `INTEGRATION_CONTRACT.md`: 기존 상태·권한·실행 체계를 보존하는 연결 방법.
4. `office.scene.json`, `office.assets.json`, `office.visual-states.json`: 장면과 표현 계약.
5. `ART_ASSET_GUIDE.md`, `implementation.plan.json`: 제작·개발 순서.

## 현재 명세의 결정

- `#/office`는 메인 대시보드로 유지한다.
- `#/office/room`에 픽셀 사무실을 추가한다. 상단 `대시보드 | 픽셀 사무실` 전환을 사용한다.
- 실제 앱 라우트가 다르면 기존 링크를 유지하는 alias를 제공하고 변경표를 보고한다.
- React UI + PixiJS 8.x를 기본안으로 한다. 기존 앱에 동등한 렌더러가 이미 있으면 중복 설치하지 말고 차이를 설명한다.
- 기본 범위는 고정 시점 2.5D이다. 3D 회전, 물리엔진, 자유 보행, 자동 AI 채팅은 추가하지 않는다.
- 사무실 화면은 기존 도메인의 읽기 전용 표현 계층이다. 별도의 실행·승인·업무 DB를 만들지 않는다.
- 각 자리의 seed 이름은 실제 member ID가 아니다. 기존 member와 명시적으로 연결하고 미연결은 미연결로 표시한다.
- Gemini와 NotebookLM은 시각적으로 별도 자리를 둔다. 실제 팀원이 하나라면 두 독립 실행자로 복제하지 않는다. 별도 역할 등록 여부는 설정에서 명확히 처리한다.

## 보존해야 할 경계

기존 지시·승인·검사·재시도·보안·동시 실행 한도는 바꾸지 않는다. 원본 v1 명세의 안전 규칙은 그대로 따른다. 사무실에 5명이 보인다고 5개 실행을 자동 시작하지 않는다. 기본 PC당 1개 관리형 실행 정책을 유지한다.

기존 WIP와 다른 개발자의 변경을 덮어쓰지 않는다. 기존 환경에서 `git status`와 브랜치를 확인하고 작업 범위를 기록한다. 저장소 전체 reset, force push, 기존 파일 대량 재작성, main 직접 수정, 운영 배포를 하지 않는다.

명령과 권한은 기존 서버 API만 사용한다. 캔버스 클릭·캐릭터 이동·애니메이션 완료가 작업 완료, 승인, 자동 배포를 발생시키면 안 된다.

## 실제 상태 표시

관리형/관찰형 실행의 최신 Runner 확인이 있을 때만 작업 동작을 반복한다. AI 자체 보고와 사용자 수동 보고는 구분한다. 일반 ChatGPT/Gemini/NotebookLM 웹 탭을 자동 관찰한 것처럼 만들지 않는다.

실행 성공과 업무 완료는 다르다. 연결이 끊겼다고 실행 실패·종료로 바꾸지 않는다. 수동 보고는 보고 시각을 표시하며, 가짜 heartbeat를 만들지 않는다. 데모를 켜려면 명시적인 데모 배지가 있어야 한다. live 화면에서 데모 fixture를 기본값으로 불러오지 않는다.

## 구현 순서

먼저 저장소 구조·라우트·스토어·컴포넌트·테스트 방식·API 실제 유무를 확인하고, 이 명세와 다른 점을 짧게 기록한다. 백엔드가 아직 없으면 기존 인터페이스를 구현할 provider 경계를 만들되, demo-only인 상태를 명확히 표시한다.

`PX-01 → PX-02 → PX-03 → PX-04 → PX-05`로 실제 연결 구조와 상호작용을 만들고, 에셋 제작 `PX-06`과 안정화 `PX-07~09`를 수행한다. 초기에는 명시적 placeholder를 써도 되지만, 최종 화면을 단색 도형이나 개념 이미지 하나로 끝내지 않는다.

`starter/` 코드는 기존 앱에 맞게 이식할 수 있다. 단위 테스트만 통과했다고 UI·연동이 완료된 것으로 보고하지 않는다. 렌더러·React 생명주기·실제 API까지 별도로 검증하라.

## 완료 보고 양식

- 기준 브랜치/커밋 및 변경 파일.
- 실제 구현된 항목과 미구현 항목.
- 실제 연결 / 수동 보고 / 데모의 구분.
- 데스크톱·모바일 화면 캡처와 미연결·오류 상태 캡처.
- 수행한 테스트 명령·결과·실행 환경. 실행하지 않은 항목은 미실행으로 표시.
- 에셋 출처·제작 상태·남은 placeholder 목록.
- 기존 대시보드·지시·승인 기능 회귀 검사 결과.
- 검토할 쟁점. 운영 반영은 별도 사용자 승인.

사용자가 창을 열었을 때 '누가 어떤 일을 하고 있으며 내가 무엇을 결정해야 하는가'를 즉시 알 수 있어야 한다. 사무실의 따뜻한 분위기와 업무 상태의 정확성을 함께 충족하라.
