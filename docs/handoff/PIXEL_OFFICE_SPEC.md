# AI Office 1.1 — 따뜻한 픽셀 사무실 추가 명세

작성일: 2026-10-28 · 구현 대상: 기존 AI Office 프론트엔드 · 변경 범위: 시각화와 화면 연결

## 1. 결과물 정의

사용자는 기존 메인 대시보드에서 실제 업무를 관리하고, `픽셀 사무실`로 전환하면 각 AI가 고정된 자리에서 어떤 업무를 맡고 있는지 공간적으로 확인한다. 자리를 누르면 기존 작업·자료·지시·승인 기능으로 이어진다.

사무실은 단순 장식도 아니고 별도의 업무 시스템도 아니다. 같은 데이터의 두 가지 표현이다. 메인 대시보드를 없애거나 그림 뒤에 숨기지 않는다.

## 2. 시각 방향과 3D의 범위

### 기본 방식: 고정 시점 2.5D 픽셀아트

32×16 등각 타일과 독립 스프라이트로 입체감을 만든다. 카메라는 고정 각도이며 확대·이동만 허용한다. 실제 3D 메시의 자유 회전은 이번 기본 범위 밖이다. `입체 사무실`이라는 사용자 요구를 이렇게 구현한다는 점을 결과 보고에 분명히 적는다.

참고 이미지의 목제 바닥, 식물, 따뜻한 조명, 소파, 책과 커피, 각자의 책상을 계승한다. 원근이 제각각인 생성 이미지의 구도를 그대로 타일로 자르지는 않는다. 모든 제작 에셋은 같은 등각 그리드·광원·픽셀 밀도로 다시 맞춘다.

### 아트 규칙

- 배경: 크림·오크·세이지·앰버. 과도한 네온·채도 높은 게임 UI는 사용하지 않는다.
- 빛: 좌측 상단 광원. 정적인 따뜻한 하이라이트와 제한된 그림자.
- 캐릭터: 5명의 고정 외형. 의복·소품으로 구별하며 로고를 머리로 쓰지 않는다.
- 픽셀: 가구와 캐릭터의 픽셀 크기를 통일하고, 비정수 축소에서는 완전한 픽셀 정렬을 보장한다고 주장하지 않는다.
- 텍스트: 이름·업무명·시간·알림 수는 선명한 HTML UI로 표시한다. 이미지에 굽지 않는다.
- 이미지의 오류·가상 일정·날씨·날짜·진행률은 계승하지 않는다.

## 3. 정보 구조

| 위치 | 역할 |
|---|---|
| `#/office` | 기본 대시보드. 기존 행동·정보 우선순위 보존 |
| `#/office/room` | 픽셀 사무실. 장면과 하단의 접근 가능한 팀원 목록 |
| 화면 상단 | `대시보드 / 픽셀 사무실`, 프로젝트 필터, 새 지시, 상태 신선도 |
| 장면 우측 | 선택한 팀원의 상세 드로어 |
| 모바일 | 장면 아래 팀원 목록. 상세는 하단 시트 또는 전용 페이지 |

픽셀 사무실을 이전에 사용했더라도 다음 앱 기본 진입을 임의로 바꾸지 않는다. 사용자가 기본 보기 설정을 바꾸는 기능은 후속 선택 사항이다. 장면 위치·확대율은 사용자별 로컬 UI 설정으로 기억할 수 있다.

프로젝트 필터를 바꿔도 자리를 재배치하지 않는다. 다른 프로젝트의 작업은 흐리게 표현하고 '다른 프로젝트 작업 중'을 표시한다. 필터 때문에 실제 작업 중인 팀원이 '대기'로 바뀌어서는 안 된다.

## 4. 공간 구성

| 공간/자리 | 의미 | 클릭 행동 |
|---|---|---|
| GPT 작업석 | 연구·설계·검수 | 팀원 상세, 배정된 작업, 근거 자료 |
| Claude 작업석 | 구현·개발 | 팀원 상세, 변경 내역, 작업 상세 |
| Gemini 작업석 | 자료·이미지 | 외부 작업 지시 묶음·결과 등록 |
| NotebookLM 작업석 | 출처·문서 | 자료·노트북 링크·수동 결과 등록 |
| Codex 작업석 | 코드·검사 | 검사 결과, 실행 로그, 작업 상세 |
| 총괄·승인석 | 사용자의 판단 | 기존 승인함 |
| 검토·인계 테이블 | 담당 간 인계 이력 | 현재 프로젝트 작업들의 인계·검토 기록 |
| 공유 서가 | 결과·자료 | 기록·자료 검색 |
| 작업 게시판 | 진행 업무 | 기존 작업함 |
| 실행 PC 콘솔 | Runner 연결 | 기존 연결 설정 |
| 소파·커피 공간 | 분위기 | 기본 장식. 커피 클릭은 선택적 소리·움직임 설정만 |

자리의 role은 초기 제안이며 프로젝트 역할 배정으로 바뀐다. 캐릭터 이름과 실행 도구를 혼동하지 않는다. 코딩 작업을 GPT 역할이 Codex로 수행해도 두 팀원이 동시에 한 실행을 수행한 것처럼 중복 표시하지 않는다.

동시 작업이 여러 개일 때 자리를 늘리거나 캐릭터를 복제하지 않는다. `실행 1 / 대기 2 / 승인 1`처럼 분리 표시하고, 대표 작업은 서버의 현재 실행 또는 사용자 선택으로 결정한다. `최신`의 정의는 서버 순서이며 브라우저가 텍스트 시각을 보고 추측하지 않는다.

## 5. 배치와 렌더링

정확한 초안 좌표와 객체 ID는 `office.scene.json`을 따른다. 24×18 그리드, 기본 논리 화면 960×600, 타일 32×16이다. 좌표는 파일에서 수정 가능하지만 DB 상태와 섞지 않는다.

```text
screenX = originX + (tileX - tileY) × tileWidth / 2
screenY = originY + (tileX + tileY) × tileHeight / 2 - height × elevationPx
```

이 식과 역변환은 `starter/isometric.mjs`에 구현했다. 이 좌표는 공간 배치 좌표이며 기존 개념 이미지의 픽셀 좌표가 아니다.

### 겹침과 가림

전체 레이어는 architecture → floor decor → world → lighting → selection → DOM UI다. world 안의 가구·사람은 발이 바닥에 닿는 지점의 screenY, 미세 정렬값, 고정 ID 순으로 정렬한다. 이미지의 윗부분이나 캐릭터 머리 높이로 정렬하지 않는다.

책상은 적어도 rear/chair/avatar/front 순으로 분해한다. 캐릭터가 책상 위에 떠 있거나 다리가 책상 앞으로 튀어나오는 문제를 실제 이미지로 검수한다. 전경 벽·식물이 주요 클릭 영역을 가리면 장식 투명도를 낮추되 상태·텍스트를 흐리게 하지 않는다.

### 픽셀과 화면 맞춤

텍스처 nearest sampling, antialias 비활성화를 기본으로 한다. 논리 화면을 저해상도로 유지하고 화면 배율에 맞게 배치한다. DOM 텍스트는 이 저해상도 렌더링을 거치지 않는다. CSS `image-rendering`만 적용하고 내부 텍스처 보간을 그대로 두지 않는다.[S02, S04]

가능하면 정수 배율을 사용하되 모바일 맞춤에서는 비정수 배율을 허용하고 왜곡을 확인한다. pan은 픽셀에 맞추며 pointer 좌표와 DOM 라벨에는 **동일한 카메라 변환**을 사용한다. DPR을 좌표 변환에 두 번 곱하지 않는다.

기본 확대는 화면 맞춤이다. `맞춤`, `확대`, `축소`를 HTML 버튼으로 제공한다. 휠 스크롤은 페이지 스크롤을 우선하고 Ctrl/Meta+휠 또는 명시적 버튼만 확대에 쓴다. 드래그와 클릭은 이동량 임계값으로 구분한다. 모바일에서 장면 밖 스크롤을 가로채지 않는다.

## 6. 사용자 상호작용

### 자리 선택

한 번 클릭/탭 → 선택 테두리 → 팀원 상세 드로어. hover는 간단한 이름·역할만 보여주며 클릭 기능을 대체하지 않는다. 더블 클릭에 중요한 명령을 넣지 않는다.

드로어 필드: 팀원 이름, 프로젝트별 역할, 연결 방식, 실제 실행 도구, 현재 업무, 업무 상태, 실행 상태, 근거 출처, 마지막 확인 시각, 다음 행동, 대기 작업, 관련 결과물.

행동: `작업 열기`, `이 담당에게 새 지시`, `자료 보기`. 외부 작업은 `지시 묶음`, `서비스 열기`, `결과 등록`. 중지 가능 연결에만 기존 중지 요청을 노출한다. 중지 요청은 확인 대화상자와 서버 명령의 전달·종료 확인을 거친다. 연결이 끊겨도 중지 요청을 예약할 수 있는 기존 정책이라면 '전달 대기'로 표시한다.

새 지시는 기존 폼을 열어 프로젝트와 담당만 채운다. 즉시 실행하지 않는다. 드래그로 업무를 옮기거나 자리를 옮겨 담당을 바꾸는 기능은 이번 범위에서 제외한다.

### 승인과 인계

총괄석의 배지는 권한 있는 실제 승인 요청 수를 표시한다. 자리를 누르면 승인함으로 이동하며, 그림 안에서 즉시 승인하지 않는다.

인계 테이블은 인계 기록을 여는 접근점이다. 작업을 전달하는 연출은 실제 `인계 수락`이 확인된 후 한 번만 허용하는 후속 효과로 둔다. 캐릭터의 도착 자체가 인계 성공 조건이 되지 않는다. 이번 기본 버전에서는 캐릭터가 자리를 지키며, 자동 이동·자동 회의·가짜 채팅은 없다.

## 7. 상태 표시와 근거

업무 상태, 실행 상태, 연결 신선도, 증거 출처는 별개의 값이다. 시각 상태는 이 값들의 읽기 전용 투영이다. 이름이 같은 새 DB enum을 만들지 않는다.

| 실제 근거 | 화면 | 동작 |
|---|---|---|
| running + 최신 Runner 실행 생존 확인 + 연결 정상 | 작업/검사/검토 중 | 타이핑 또는 자료 보기 |
| AI의 자유 텍스트 보고만 있음 | AI 보고 | 정적 포즈 |
| 서버의 실행 상태 기록만 있고 Runner 직접 관찰은 없음 | 서버 기록 | 정적 포즈 |
| 외부 웹 작업에 대한 사용자 보고 | 외부 작업·직접 보고·보고 시각 | 정적 포즈 |
| 준비/대기열 | 배정 대기 | 작은 대기 포즈 또는 정적 |
| run succeeded, task 미완료 | 실행 종료·결과 확인 필요 | 정적 실행 종료 표시 |
| task awaiting_owner | 사용자 판단·승인 대기 | 알림 아이콘 |
| task done | 업무 완료 | 정적 완료 표시 |
| 45초 상태 지연 | 마지막 확인 + 지연 | 작업 동작 중단 |
| 90초 연결 끊김 | 현재 실행 미확인 | 작업 동작 중단. 실패로 바꾸지 않음 |
| 중지 요청, 종료 미확인 | 중지 처리·전달 대기 | 종료 완료로 표현하지 않음 |
| 상태 상충 | 상태 불일치 | 새 snapshot 조회. 조용한 보정 금지 |

45/90초는 기존 설계의 초기 임계값이지 측정된 성능이 아니다. Runner heartbeat와 실행 프로세스 생존 확인을 별도로 취급한다. 로그 출력이 잠시 없다는 사실만으로 실패라고 판단하지 않는다. 서버가 실제 프로세스 확인을 하지 못하면 단지 동작을 정지하고 상태를 미확인으로 표시한다.

가상 진행률, 임의의 현재 업무, 캐릭터의 랜덤 타이핑, AI 간 가짜 대화, 모델 내부 생각을 보여주는 말풍선은 금지한다. 화면 한 구석의 작은 '데모' 문구만으로 live 표와 섞는 것도 금지한다.

## 8. 애니메이션·오디오

기본은 미세 동작이다. idle 4fps, typing 6fps, reading 4fps 정도의 스프라이트 프레임으로 시작한다. 전체 렌더러 목표 상한은 30fps이며 높은 프레임이 제품 완료 기준은 아니다.

식물·조명·커피 김 같은 환경 효과는 업무와 무관한 장식임이 분명한 수준으로 제한한다. 산만한 연기·불꽃·모니터 번쩍임·알림 진동을 피한다. 기본 음소거. 소리를 사용자가 켠 경우에만 브라우저 사용자 동작 이후 재생한다.

`prefers-reduced-motion` 또는 화면의 `움직임 줄이기` 설정이면 모든 반복 동작을 정지한다.[S05] 탭이 숨겨졌거나 사무실을 떠났으면 ticker를 정지·해제한다. 이때 업무 구독은 앱 정책에 따라 유지할 수 있으나 픽셀 화면이 별도 구독을 중복 생성하지 않는다.

## 9. 반응형·접근성

데스크톱에서 장면이 가로 영역 대부분을 차지하고, 선택된 팀원 상세는 오른쪽에 둔다. 선택 전에는 큰 빈 패널을 남기지 않는다. 창 높이가 낮으면 장면 아래 설명보다 업무 행동을 먼저 보이게 한다.

모바일에서는 맞춤 축소 장면 + DOM 팀원 목록이 기본이다. 44 CSS px 이상의 조작 영역을 확보한다. 작은 스프라이트만 누르게 하지 않는다. 상세를 열면 읽을 수 있는 너비의 하단 시트/전용 페이지를 사용한다.

키보드 Tab으로 팀원 목록·공간 접근점·확대 버튼·드로어 행동에 접근한다. Enter/Space 선택, Escape 닫기, 닫은 뒤 원래 버튼으로 초점을 돌린다. 실제 modal일 때만 포커스를 가둔다. 상태는 색상뿐 아니라 텍스트와 아이콘으로 표시한다. 한글 본문은 기본 14px 이상을 목표로 한다.

캔버스는 시각 표현으로 두고 같은 기능을 제공하는 DOM 목록을 유지한다. 스크린리더에 동일한 선택지를 캔버스 오버레이와 별도 목록으로 두 번 읽히지 않게 한다. `aria-live`는 검증된 주요 전환만 묶어서 읽고 매 프레임·초 단위 시각을 낭독하지 않는다.

## 10. 리소스·오류 처리

픽셀 사무실 라우트를 열 때만 렌더러와 에셋을 로딩한다. 대시보드 첫 진입에서 무거운 장면을 강제 로딩하지 않는다. 앱이 WebGL을 생성하지 못하거나 context가 손실되면 React 오류 안내와 DOM 목록을 유지한다. PixiJS가 어떤 브라우저에서든 자동 Canvas fallback을 제공한다고 가정하지 않는다.

이미지 로딩 실패는 해당 자리의 명시적인 대체 도형과 이름으로 처리한다. 실패 상태를 숨기고 실제 캐릭터가 완성되었다고 보고하지 않는다. 초기 아틀라스 압축 전송 목표는 4MB 이내, 선택 장식 포함 8MB 이내로 시작하며 실측 후 보고한다. 압축 용량과 GPU 메모리를 혼동하지 않는다.

React mount/unmount와 비동기 renderer 초기화 경합을 처리한다. 초기화 중 unmount되면 완료 후 즉시 정리하며 canvas를 다시 붙이지 않는다. Strict Mode 반복 mount에서도 Application/ticker/ResizeObserver/구독이 중복되지 않아야 한다.[S01, S06]

20회 진입·이탈, 숨김 탭, 창 크기 변경, 느린 에셋 응답, context 손실을 시험한다. 실제 사용자 PC/Whale 성능을 이 패키지 단위 테스트로 보장하지 않는다.

## 11. 개인정보·권한

실행 명령·API 키·CLI 토큰은 장면 JSON에 들어가지 않는다. 업무명·로그·보고서의 HTML을 실행하지 않는다. React 텍스트 노드를 사용하고, Markdown은 기존 안전한 렌더러를 사용한다. 외부 링크는 허용한 https 주소로 제한하고 새 창은 noopener/noreferrer를 사용한다.

사진 촬영·화면 공유용 `업무명 숨기기` 모드를 권장한다. 이 모드에서는 프로젝트명·작업명·자료 미리보기를 숨기고 역할과 상태만 남긴다. 모드는 UI 프라이버시 기능이지 서버 권한 대체가 아니다.

장면 파일에 URL이나 메서드를 넣어 임의 API를 호출하지 않는다. `action`은 고정 enum을 기존 라우트/명령 핸들러에 매핑한다. JSON의 지시문을 셸 명령으로 실행하지 않는다.

## 12. 단계별 완료 기준

P0-연결 구조: 기존 라우트 보존, 명시적 member 바인딩, 같은 스토어, 팀원 상세 연결.

P0-시각 완성: 독립 가구·캐릭터, 따뜻한 픽셀 스타일, 가림 처리, 제작 완료 에셋, 한글 DOM 표시.

P0-실제 검수: 하나의 관리형 실행과 하나의 외부 수동 작업을 실제 앱에서 확인, 양쪽 보기의 동일 task 상태 검증, 오류·재연결·승인 회귀 시험.

P1 이후: 사용자별 테마, 자리 배치 편집, 서버에서 확인된 인계의 1회 이동 효과.

P2 별도 승인: 실제 3D 카메라 회전, 멀티룸, 자유 보행. 추가할 경우도 기존 업무 데이터와 분리한다.

**명세·기초 코드·단위 테스트는 개발 출발점이다. 통합된 화면과 실제 연동을 검사하기 전에는 픽셀 사무실이 완성되었다고 보고하지 않는다.**
